Data Access Patterns: Source FeatureGroups

Overview

mloda reads data through source FeatureGroups (files, documents, databases and custom sources).

For practical examples of data access methods, see Data Access Overview.

Data Sources

  • Source FeatureGroups: one FeatureGroup per kind of source, claiming features through CLAIM_ROUTES:
    • ReadFileFG with CsvFG, ParquetFG, JsonFG, FeatherFG, OrcFG (see access-feature-data)
    • ReadDBFG with SqliteFG
    • DuckdbFG: reads the tables and views of a DuckDB connection in the DataAccessCollection, only when the feature's connection_handle names it (Feature("amount", connection=conn) sets one). On DuckDB it hands over a lazy relation on your connection, so later DuckDB steps run as SQL; elsewhere it loads a pa.Table. It reads the main schema of the connection's current database; a connection_handle forwarded from a consumer counts too. A feature tied to a DuckDB connection whose table has a column of that name is read from the table, so if another group also serves that name, resolution reports both groups (leave DuckdbFG out of the plugin collector, or rename). Off DuckDB it reads through a separate cursor, which sees committed rows only. mloda never closes the connection.
    • ReadDocumentFG with TextFG, PyFG, MarkdownFG, YamlFG, JsonDocumentFG; documents skip suffixes owned by ReadFileFG groups by default
  • DataCreatorFeatureGroup: For generating synthetic data (see access-feature-data)
  • ApiDataFG: A source FeatureGroup for runtime data injection (see access-feature-data)

Writing a source FeatureGroup

Subclass the base that fits your source and write only what it asks for. The base owns the matching: claim routes, source discovery, pointers, data_access_handle, column_to_file, per-run caching, ambiguity and missing-column errors, and the extender hook around the load.

A source group can also describe its data through declared_attributes, see Declared Attributes and Input Requirements.

  • SourceFeatureGroup (any source): declare CLAIM_ROUTES, implement find_sources and load_neutral; optionally columns, has_column, ambiguity_fix (the default hint names data_access_handle only if the group declares it in PROPERTY_MAPPING; override it if the group takes no pointer), describe_columns, count_rows, and match_connection when the source is a connection in the DataAccessCollection (the planner then keeps the read on a framework that accepts it), neutral_type when load_neutral returns one type (a run without a compute_frameworks list then prefers a framework that takes it as is). query_text is reserved: a group whose routes do not require it declines, and aborts when pointed. To honor data_access_handle like the stock bases, declare PROPERTY_MAPPING = {HANDLE_OPTION: HANDLE_SPEC} (both from mloda.provider); without it a non-str handle is not rejected. A NamePolicy.DECLARED route claims the names in declared_names() and those starting with a prefix from declared_name_prefixes() or <ClassName>_ (not the bare prefix itself); the check also runs when a request points at the group, which then declines before any source probe. A prefix does not claim a name holding __ from the prefix's last character on, so a chain such as <prefix>x__sum_aggr goes to the group that computes it (list such a name in declared_names() to claim it).
  • ReadFileFG: implement suffixes() and column_names(path). It inherits file and folder discovery, the pinned-file rule, and a default load_neutral that hands a FileSource to the compute framework; the stock FileSource transformers read csv, parquet, json, feather and orc.
  • ReadDocumentFG: implement suffixes(); optionally read_text and handover_suffixes. It inherits the three names <Group>, <Group>~source and <Group>~file_type.

  • ReadDBFG: implement is_valid_credentials, database_identity, connect, list_tables, table_columns and produce_rows. is_valid_credentials must never raise. database_identity must not contain credential values. login_key(credentials) returns a credential-free hashable where equal keys mean the same login (default: a keyed digest of the credentials without table_name, with values that are not plain scalars compared by equality); two logins on one source are told apart by data_access_handle. Override login_key when credential fields that do not change grants (timeouts, application names) differ between handles. data_access_identity names the dataset, not the login. The table catalog is cached per run per login (login_key) and preset table; with a preset table_name, only that table's columns are read. rechecked_filters(features) gives the filters a read may push into its query, since the framework applies them again after the load. A subclass whose calculation uses the loaded rows beyond loading them (ranks, totals) overrides rechecked_filters to return []. SqliteFG pushes exact numeric and text-equality shapes into a parameterized WHERE and leaves everything else to the post-read filter, so a run that succeeds today returns the same rows; it pushes only when each untyped column holds one storage class, and a typed filter column only when its type matches the declared affinity (INT64, DOUBLE, STRING). To check credentials against PropertySpecs, use validate_property_values and convert its error:

    ```python from typing import Any

    from mloda.provider import PropertySpec, PropertyValidationError, validate_property_values

    CREDENTIAL_SPECS = {"host": PropertySpec("Database host")}

    def is_valid_credentials(credentials: dict[str, Any]) -> bool: try: validate_property_values(credentials, CREDENTIAL_SPECS, closed_world=True) except PropertyValidationError: return False return True

    assert is_valid_credentials({"host": "db"}) assert not is_valid_credentials({"host": "db", "password": "secret"}) ```

  • ReadDBFG query route: opt in with CLAIM_ROUTES = (*ReadDBFG.CLAIM_ROUTES, ReadDBFG.QUERY_ROUTE) and implement produce_query_rows(connection, query_text, features). A query-only group lists just (ReadDBFG.QUERY_ROUTE,) and stubs the table hooks. The source is a hash of the query text, so textually different queries are different sources. Without a pointer the route claims any leaf name for each matching credential in the DataAccessCollection, and it switches off the table route for that feature. A derived name such as price__sum_aggr goes to the group that computes it; feature_group=<Group> overrides that.

A source group's PROPERTY_MAPPING is merged over the declarations of every class in its MRO, mixins included, even when the group declares none of its own: own keys win and base keys cannot be dropped, so PROPERTY_MAPPING = None on a source group raises TypeError. Class definition is checked: a ClaimRoute with a wrongly typed field, a file or document route whose source_kind is not "file" or "folder", and suffixes() that does not return a non-empty tuple of non-empty strings all raise TypeError. A concrete group's suffixes() runs at class definition.

A source group reports match.source as its data_access_identity; override it to publish a richer identity. Run the reader suites read_file_suite, read_db_suite, read_document_suite and loads_into_framework_suite (it checks the group loads into the host's compute framework, one host per framework) from mloda.testing.source against your group; they pin the behavior every source group shares.

A family of groups shares an abstract base, which declines; each concrete subclass matches itself through the base's path. Customize discovery through CLAIM_ROUTES and find_sources, which run behind the INPUT_DATA_MATCH gate. An override of match_feature_group_criteria calls super() and runs any extra I/O through gated_probe (see Extender). Another group asks whether a source group has data in reach with has_source(options, data_access_collection, feature_name), which applies matching's route selection without claiming. True means a selected route's find_sources returned a match, not that the source is readable or holds the named column. Pass the name you are about to claim so gates see it.

A derived group should declare its dependencies in input_features and match names and options without probing readers itself. Resolution checks competing groups' input chains in the run's environment.

For example, a derived group and a CSV column may both claim revenue. The CSV route yields when the derived group's input chain resolves; if that chain has a missing or refused input, the CSV column remains available. Use feature_group=CsvFG to scope the request to the CSV source.

CSV inference semantics are defined by pyarrow's default CSV reader; the stdlib reader behind PythonDict follows it. Types are inferred per column: null tokens (pyarrow's default set, e.g. NA, NaN, null) become None in an int/float/bool column but stay literal text in a string column, a column of only empty cells and/or null tokens is all-None, and an int column with a value outside signed int64 range degrades entirely to float.

Loaders and compute frameworks

A database implementation receives data.access as a DBTable (or a DBQuery on the query route), both from mloda.provider. A subclass that changes parsing (for example a semicolon CSV overriding only column_names) must also override load_neutral, otherwise the inherited neutral form and the inherited implementations still parse the parent format.

A per-framework fast path is an Implementation[YourFG] (from mloda.provider): set feature_group (a SourceFeatureGroup subclass) and compute_framework, and write a classmethod calculate(group, data, features, framework) that returns the data (data is the SourceMatch). At plan build mloda picks one per step over the governed set, walking the group MRO, then the framework MRO, most specific pair first; the serving subclass is passed as group. A class that overrides load_neutral cuts off implementations inherited from above it, and a subclass of an implementation replaces it. Two implementations of one exact pair where neither subclasses the other stop the environment build with EnvironmentPreconditionError. Without an implementation the group loads load_neutral and a transformer converts. An implementation must stay referenced: define it at module level, because an unreferenced class is garbage-collected and no longer found. An __init_subclass__ override must call super().__init_subclass__(), or the implementation is not found. Disable one with PluginCollector.add_disabled_implementation_classes. Calls made without an engine (count_rows) see every loaded implementation, not the governed set. Implementation.version() hashes the class like a FeatureGroup's. PlanStep, the plan lock and HookContext.implementation record which implementation ran.

The stdlib reader does not yet cover pyarrow's full surface. Where they differ, a column pyarrow types stays a string column in PythonDict: dates, timestamps and times, whitespace-padded numbers (" 1 "), inf/infinity, uppercase NAN (the float value, not the NaN null token), hex literals (0x1f), and a true/1 mix (pyarrow reads 1/0 as bools too).

Column discovery and row counts

describe_columns(match) maps column name to DataType (None where unknown) and raises NotImplementedError when the group cannot enumerate columns, ImportError when a backend it needs is missing, and OSError or ValueError for an unreadable source. ReadFileFG lists the names from column_names; ParquetFG, FeatherFG and OrcFG report the types stored in the file's schema, JsonFG the types pyarrow infers while parsing, and SqliteFG SQLite's declared (unenforced) column types. A document group reports its three names as strings.

count_rows(match, compute_framework) returns the row count of the source without loading it, or None when only a read can tell (the default). ParquetFG, OrcFG and FeatherFG count from file metadata for every compute framework; CsvFG only under PythonDict, since other frameworks read CSV through pyarrow, whose row split can differ; a document group counts one. With text_lines the plan-time estimate still counts each document as one row; the result-size max_rows check after the run still applies. The count is of the source itself, not of the step's output: filters, extenders and feature-group logic may change what the step reports. Both are called on the group with the SourceMatch; from a prepared session use session.describe_columns(step) and session.count_rows(step) (see the mloda API page).

Documents as features

A chained feature can read a document group. TextFG returns the whole text in one row; text_lines turns that into one row per non-blank line, with ~source and ~file_type repeated per row. Chained features such as TextFG__upper pass the option on to TextFG.

Feature("TextFG__upper", options=Options(group={"text_lines": True}))
Feature("TextFG~source", options=Options(group={"text_lines": True}))

Pointing a feature at a source

  • options={"CsvFG": path} points the group at one file (or folder). The class object works as the key too (options={CsvFG: path}), and a data_access_name() override does not add an alias pointer: only class names point. A subclass also answers to its parent's name, so Feature("x", options={"CsvFG": path}) reaches a CsvFG subclass. A pointer makes the other source groups skip the collection, and a pointer at a group that is not accessible in the run raises, naming the filter that dropped it.
  • options={"SqliteFG": Credential(sqlite="/x.db")} points a database group at one database. A plain-dict pointer works too: the matched options hold it as a RegisteredCredential, so str(options) masks its values. Prefer Credential for secrets: a pointer forwarded to a consumer prints raw there.
  • Feature(name, options={"query_text": ..., "<Group>": Credential(...)}) runs a query on a database group that opts into ReadDBFG.QUERY_ROUTE; a group without the route declines when unpointed and aborts when pointed.
  • Feature(..., feature_group=CsvFG) scopes resolution to that group (and its subclasses) without choosing a source.
  • data_access_handle only narrows: it picks one of the sources the DataAccessCollection holds and never points a group at a source the collection lacks.
  • column_to_file pins columns to files in the DataAccessCollection; a pinned file that cannot serve the request aborts instead of falling back (see access-feature-data).

The matched pair lives on Feature.input_data_match, never in the options, and is handed to the loader at load time. The source may hold credentials, so use PlanStep.data_access_identity (or Group.data_access_identity(match) outside a plan) for display and logs. If your own error text may carry a credential, scrub it with mloda.provider.scrub_credentials before logging.

Non-file sources such as HTTP

Write a SourceFeatureGroup subclass with a pointed-only NamePolicy.OPEN claim route: it claims a name only when pointed at (options={"MyApiFG": url} or feature_group=MyApiFG). Implement find_sources and load_neutral to fetch and return the data. A plain FeatureGroup is not a pointer target. A key that differs from a loaded source group's name only by case raises a SourcePointerError; a key naming a group that is not loaded is an unknown option key and is ignored. ApiDataFG injects in-memory data passed through the API request and is not an HTTP client.

Resolution of a pointed group vs feature-group resolution

Source selection runs inside feature-group resolution: the group's matcher is the criteria gate, so a group is accessible, scoped and framework-checked like any other feature group. Several sources found for one name in one group are an error naming them and the fix; two groups finding the same column is ordinary feature-group ambiguity (fix with feature_group=, a pointer or data_access_handle). See Resolution errors.

Declining with an attributable reason

A source group that owns a source but cannot serve the requested feature records why it declined; the reason then appears in the near-miss block of the "No feature groups found" error message, labeled (input data). record_match_rejection is exported via mloda.provider. A custom ReadFileFG group owns its own suffix and lists its columns; a ValueError from column_names declines the file with a recorded reason, for example a required schema marker in the header:

from typing import Any

from mloda.provider import FeatureSet, ReadFileFG

class SensorCsvFG(ReadFileFG):
    @classmethod
    def suffixes(cls) -> tuple[str, ...]:
        return (".sensorcsv",)

    @classmethod
    def column_names(cls, path: str) -> list[str]:
        with open(path, encoding="utf-8") as handle:
            header = handle.readline()
        if "#sensor-schema" not in header:
            raise ValueError("its header lacks the #sensor-schema marker")
        return header.replace("#sensor-schema", "").strip().split(",")

    @classmethod
    def load_neutral(cls, match: Any, features: FeatureSet) -> Any: ...

The recorded decline renders as a near-miss line of the resolution failure:

  - SensorCsvFG (input data): SensorCsvFG matched /data/run1.sensorcsv but could not read its columns: its header lacks the #sensor-schema marker [code: source_unreadable]

Rules for source group authors:

  • Record only when ownership is established but the content fails: right suffix but a missing column, valid credentials but a declined feature. Plain non-matches (wrong suffix, invalid credentials, a name the group does not declare) stay silent. A group that checks declared names in full, such as ReadDocumentFG, records name_not_declared for a numbered form of a declared name.
  • A request that points at no source group, for a name a NamePolicy.DECLARED route declares, records <Group> found no source serving '<name>' (source_not_found; like a pointed group's was pointed at but found no source, it names any unset option keys that left sources unsearched) when no source is found, unless the group recorded a reason first; record in find_sources only for a more specific reason.
  • Never raise to decline: a hook that raises anything but OSError, ValueError or ImportError from column_names (or an unmarked NotImplementedError where a base documents it) ends matching for that candidate. A raise marked with escalate_match_abort propagates. Record, then return a falsy value.
  • Recording outside an engine-opened window is a no-op, so groups stay usable standalone. In tests, use collect_match_rejections (see Feature Group Matching).
  • Recorded reasons are discarded at the enclosing candidate level: when the group ultimately matches, or when the feature group matches by another rule. Only a decline surfaces them.
  • Name the group and the concrete source in the reason, as the example does. The first recording per owner wins, so a later reason under a name already used in the same window is dropped; only the missing-column summary replaces a reason the same group recorded during its own probe.
  • A ReadFileFG subclass whose column_names raises NotImplementedError is eliminated for every feature name. One that raises ImportError declines any name, with a recorded reason. A file pinned with column_to_file aborts with a missing-column message ("column ... is in none of the sources", or "could not list the columns of any of its sources" when none can list). A ReadDocumentFG subclass declines any name other than its three declared names.
  • In ReadFileFG matching, an unpinned file whose columns cannot be read (OSError, ValueError) is declined with a recorded reason, so a shipped file group needs the file to be readable when features resolve. A pinned or pointed file that cannot be read aborts with the missing-column error instead of falling back to another file.

ReadFileFG column validation and the ReadDBFG catalog check already record automatically, and unpointed declared names get the default above; a custom group only needs this for its own decline points.

A feature_group= scope is final: only the scoped group and its subclasses are candidates. A class-name pointer is final against other source groups and the DataAccessCollection. A pointed group can end its match in two ways:

  • It aborts, for example on a query_text it cannot serve, a refusal at INPUT_DATA_MATCH, or a missing column. These aborts are deferred: they yield to a candidate that computes the feature from input features, or to a subclass of the pointed group that takes it over. A sole consumer's missing input is therefore reported at that input. The several-sources ambiguity abort is not deferred and always raises.
  • It declines, for example on a PROPERTY_MAPPING value or required-key failure, a missing required_options key, no source found, or a name the group does not declare. A group pointed only because the scope names a concrete ancestor does not abort on a missing column, a refused source or an unserved query_text; it declines, and records none of the no-source-found, undeclared-name or missing required_options declines, so the family member the request selects records its own reason. A plain FeatureGroup that claims the name by its own rules still serves it.

Since group options forward to input features, a pointer on a derived feature binds its inputs too (see Resolution errors). This also holds when the request is scoped to the derived group with feature_group=; a scope on a source group still rejects a pointer at a different source group. A pinned group that matches nothing without a recorded reason is reported under its own name.

Connections

A source binds its credential at match time; any group, a source included, can also read a declared handle at run time with read_credential (see Runtime access versus match-time binding).

Credential values are masked in errors and logs except under known connection fields (see named data access handles).

A connection lives in the DataAccessCollection, and the framework binds the single one it accepts. Pin one with connection_handle or Feature(name, connection=conn) (see Selecting a connection and Framework Connection Object). A source group that reads a connection declares ClaimRoute("connection", ...) and match_connection (see DuckdbFG); choosing a connection by its content happens in the source group's find_sources (see DuckdbFG.find_sources), while match_connection reports which connection a match reads.

class DuckDBAnalyticsFeature(DataCreatorFeatureGroup):
    @classmethod
    def feature_names_supported(cls) -> set[str]:
        return {"analytics_input"}

    @classmethod
    def compute_framework_rule(cls) -> set[type[ComputeFramework]] | None:
        return {DuckDBFramework}

Feature("analytics_input", connection=conn)

Integration with Other Concepts

Compute Frameworks

  • Source FeatureGroups and DataCreatorFeatureGroup: work with all compute frameworks
  • Connections: only frameworks that take a connection object (like DuckDB) bind one

For more information, see: - Compute Frameworks - Framework Connection Object - Compute Framework Integration

Feature Groups

These patterns are fundamental to how feature groups access data. For more details, see: - Feature Groups - Feature Group Matching

Best Practices

  • Use source FeatureGroups for files, documents and databases, ApiDataFG for runtime data and DataCreatorFeatureGroup for synthetic data.
  • In a source group, focus on robust source discovery, error handling and performance.
